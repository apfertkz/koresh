# Обновления: одно тело, много установок

Код «Кореша» живёт в ОДНОМ образе: `ghcr.io/apfertkz/koresh`. У каждого клиента свой Railway и свои ключи, но сервис
собирается из этого образа. Починил раз, выпустил тег, клиенты подтянули. Образ собирает CI репозитория
(файл `image.yml` в каталоге CI), руками ничего собирать и пушить не надо.

## Теги

| Тег | Откуда | Кто на нём сидит |
|---|---|---|
| `stable` | тег `v*` в репозитории | ВСЕ клиенты |
| `1.2.3` | тот же тег `v1.2.3` | никто, это архив и точка отката |
| `latest` | каждый push в `main` | только наша тестовая установка |
| `sha-<коммит>` | каждая сборка | никто, точка отладки |

Клиентский сервис всегда смотрит на `ghcr.io/apfertkz/koresh:stable`. `latest` клиентам не даём: он может смотреть на
непроверенное. Версию сервис показывает в `/health` (`APP_VERSION` зашит в образ при сборке: `1.2.3` или `sha-<коммит>`).

## Выпуск новой версии

1. Правки в `main`, `python selftest.py` зелёный (CI всё равно прогонит ворота и не соберёт образ, если красно).
2. Push в `main`: CI собирает `latest` и `sha-<коммит>`. Наша тестовая установка (отдельный сервис на Railway, образ `:latest`)
   подтягивает его. Прогнать руками: «привет», «включи свет», замок без фразы (должен отказать), `/health` показывает версию.
3. Всё хорошо: поставить тег, CI соберёт и сдвинет `stable`:

```bash
git tag v1.0.0 && git push origin v1.0.0
```

4. Клиенты подтягивают сами (см. ниже).

## Как клиенты подтягивают (по официальной доке Railway)

Источник: https://docs.railway.com/deployments/image-auto-updates (и https://docs.railway.com/services).

- Автообновления работают только для образов Docker Hub и GHCR (ghcr.io). Наш GHCR подходит. Пакет должен быть публичным.
- Для нефиксированного тега (`stable`, `latest`, `canary`; не semver) Railway перевыкатывает сервис, когда в тот же тег
  запушен новый образ. Тег в настройках Railway не меняет.
- Включается в сервисе: Settings -> Source -> **Configure Auto Updates**: тип обновления и окно обслуживания. Окна: Weekends,
  Night (02:00-06:00 UTC), Anytime, Custom. Все расписания считаются в UTC.
- Обновление применяется не в момент публикации, а после того, как Railway заметил новый образ: результат проверки
  кешируется до нескольких часов. Мгновенного обновления не ждать.
- Перед обновлением Railway делает бэкап томов сервиса («Auto Update {image}»), по доке только на тарифе Pro. У клиентов на Hobby
  бэкапа нет: память в `/data` при обновлении сохраняется (Volume переживает перевыкат), но страховки на случай поломки нет.
- Обновление перевыкатывает сервис и кратко прерывает его (для сервисов с томом по доке возможен простой).
- Админам воркспейса приходит уведомление с версиями.

**Выбранная схема.** Каждый клиентский сервис создаётся из шаблона на `:stable`. Оператор при установке включает Auto Updates
с окном на ночь клиента (Custom, в UTC; для Алматы UTC+5 это, например, 21:00-01:00 UTC). Выпустили тег `vX`, `stable` сдвинулся,
у клиентов обновление приедет в ближайшее окно после того, как Railway заметит новый образ. Участие клиента: никакого.

**Срочный случай или автообновление не сработало:** в сервисе у клиента Deployments -> три точки на последнем деплое ->
**Redeploy** (или Ctrl+K -> «Redeploy source image»): Railway заново тянет тег и запускает свежий образ. Без нового образа
деплоится тот же. Это делает оператор на экране клиента или сам клиент по просьбе.

**Что не проверено живьём:** подтягивает ли сервис, созданный из шаблона, обновление `stable` сам и за сколько (в доке про шаблоны
этого нет), и сохраняется ли включённая настройка Auto Updates у сервиса из шаблона. Первым делом проверить на тестовой установке
(выпустить пустую версию, сдвинуть тег, замерить). Пока не проверено, клиентам не обещать «обновляется само».

## Проверить, кто на какой версии

Домены клиентов знаем (мы их ставили). В приватном файле (не в репозитории) держим список, и:

```bash
while read d; do echo "$d $(curl -s --max-time 5 https://$d/health | tr -d '\n')"; done < clients.txt
```

`/health` отдаёт версию, тон, модель, включены ли замки и есть ли токен умного дома. Секретов в нём нет.

## Откат

Сломали выпуск: сдвинуть `stable` на прошлую версию (нужен docker с входом в GHCR и токен с `write:packages`, делает владелец):

```bash
IMG=ghcr.io/apfertkz/koresh
docker buildx imagetools create -t $IMG:stable $IMG:<ПРОШЛАЯ_ВЕРСИЯ>
```

Клиенты откатятся тем же механизмом, что и обновлялись, то есть в своё ближайшее окно. Срочный случай: Redeploy (см. выше).
Честно про риск: автообновление раздаёт ошибку всем сразу. Поэтому порядок строгий: ворота, потом `latest` у нас, потом тег `v*`.

## Правила совместимости (чтобы обновление не ломало чужие установки)

1. Новая переменная окружения НИКОГДА не обязательная. У неё есть значение по умолчанию в `config.py`. У старых клиентов её нет, и они должны жить.
2. Старую переменную не переименовываем и не убираем. Нужно переименовать: читаем обе, новая главнее.
3. Меняется что-то ломающее (формат `HOUSEHOLD`, смысл тона и т.п.): выпускаем отдельный поток `stable-2` и переводим клиентов вручную, а `stable` не трогаем.
4. Состояние диалога живёт в памяти процесса, при обновлении сбрасывается. Это нормально. Долгая память лежит в Volume `/data` и обновление переживает.
5. Секреты и данные клиента в образ не попадают: всё через переменные. Поэтому образ публичный.

## Что нужно сделать один раз владельцу

- Сделать пакет GHCR публичным (иначе клиенты не смогут тянуть образ): `ПУБЛИКАЦИЯ-команды.md`.
- Собрать шаблон Railway по `ШАБЛОН-railway.md`.
- Тестовая установка на `:latest` на нашем аккаунте.
